# Промпт для аудита и развития Настеньки

Ты работаешь с существующим Telegram-ботом «Настенька» для инженерной компании
ООО «НТЦ Митра». Репозиторий: `abduzarr-arch/Nastenyka_STC-Mitra`. Бот развёрнут
на Railway, использует Python, `python-telegram-bot`, SQLite на постоянном томе,
DeepSeek/OpenAI, Tavily и API YouGile.

Владелец продукта не программист, а инженер-конструктор и директор. Объясняй
результат простым русским языком: что было не так, что изменено, как проверить
в Telegram и нужны ли новые переменные Railway. Не ограничивайся общими советами:
сначала изучи реальный код, затем предложи и реализуй только обоснованные правки.

## Назначение бота

Настенька должна работать как операционный ассистент компании:

- отвечать сотрудникам только при прямом обращении к ней;
- помнить рабочие чаты и видимых участников;
- изолировать контекст разных чатов и разных сотрудников;
- хранить задачи, договорённости, статусы и напоминания;
- синхронизироваться с YouGile и давать руководителю понятные сводки;
- собирать фактические трудозатраты (ТРЗ) сотрудников;
- анализировать и редактировать Word/Excel/PDF без разрушения исходных файлов;
- принимать голосовые команды;
- использовать интернет-поиск только когда он нужен.

## Главные проблемы для проверки

### 1. Тишина в групповых чатах

В группах бот не должен отвечать на обычную переписку. Допустимые причины ответа:

- точное `@username` бота;
- явный ответ Telegram на сообщение бота;
- команда `/ask@username_бота ...` или другая команда бота;
- настроенное имя-триггер только как отдельное прямое обращение в начале текста,
  например `Настенька, помоги`.

Фразы `мы спросим Настеньку позже`, `этот бот вчера отвечал`, `ботинок нужен для
модели` не являются обращением. Проверь одинаковые правила для текста, голоса,
фото и документов. Учти Telegram Privacy Mode: при отключённом режиме бот видит
всю переписку, но всё равно обязан молчать без обращения.

### 2. Надёжный сбор ТРЗ

Сохранение ТРЗ должно быть детерминированным, без обращения к LLM. Поддержи:

```text
/trz Объект | Выполненная работа | 6 | 28.07.2026
ТРЗ: Объект | Выполненная работа | 6
```

и заполненный шаблон, в котором список работ может быть многострочным:

```text
"28.07.2026" - дата работ
"*Сигнальный" - объект на котором выполнялись работы
"*3" - ТРЗ в часах
"*Созвон и ознакомление с ИД
Добавление новой стены" - список работ выполненных за отчётный день
```

Такое сообщение является новой записью, а не запросом отчёта. После записи бот
обязан вернуть подтверждение с ID, сотрудником, объектом, работой, часами и датой.
Повторная доставка одного Telegram-сообщения не должна создавать дубль. Ошибка
разбора должна называть конкретное неверное поле. Нужны удаление/исправление
ошибочной записи и отчёты по периоду, объекту и сотруднику.

Отдельно спроектируй следующий этап, не включая его молча без согласования:

- опциональный ежедневный запрос ТРЗ в выбранных рабочих чатах;
- список «сдали / не сдали» по активным сотрудникам;
- напоминание только тем, кто не отчитался;
- время и рабочие дни через переменные Railway;
- сводка руководителю по объектам, людям и отклонениям;
- сопоставление названий объектов с проектами YouGile без потери исходного текста.

### 3. Контекст, скорость и отсутствие смешения тем

Проверь ключ истории диалога: в группе история должна быть отдельной для пары
`chat_id + user_id`, в личке — для пользователя. Не сохраняй в историю повторно
большие служебные блоки, списки всех чатов/участников и выгрузки задач. Ограничь
историю числом сообщений и общим размером. Справочник сотрудников добавляй в
LLM-контекст только для вопросов о людях, назначениях и межчатовых действиях.

Измерь или оцени основные задержки: сетевой вызов модели, онлайн-поиск, размер
промпта, извлечение файлов и повторные API-вызовы. Не отправляй запрос в LLM для
команд, которые можно надёжно разобрать кодом.

### 4. YouGile и внутренние задачи

YouGile должен быть основным источником фактов о проектах и задачах, если API
доступен. Не показывай пользователю технические UUID без необходимости. Ответы
должны быть человекочитаемыми: проект, доска/колонка, задача, исполнитель, срок,
статус. Внутренний задачник бота не должен выдавать себя за данные YouGile.
Опиши явные правила синхронизации и поведение при недоступности API.

### 5. Надёжность и безопасность

- Не читай и не выводи значения API-ключей и Telegram-токена.
- Не удаляй рабочую SQLite-базу и файлы постоянного Railway Volume.
- Не перезаписывай исходные Word/Excel-файлы; создавай новую копию.
- Не откатывай изменения владельца в грязном git-дереве.
- Не добавляй тяжёлые зависимости без доказанной необходимости.
- Логи должны объяснять этап и ошибку, но не содержать секретов или полный текст
  конфиденциальных документов.

## Обязательные проверочные сценарии

1. Два сотрудника по очереди задают разные вопросы в одной группе: контексты не
   смешиваются.
2. Одинаковый сотрудник пишет в двух группах: истории не смешиваются.
3. Обычная фраза с именем бота внутри предложения остаётся без ответа.
4. Прямое обращение в начале, `@mention`, reply и команда получают ответ.
5. Многострочный шаблон ТРЗ выше сохраняется с датой `28.07.2026`, объектом
   `Сигнальный`, значением `3` часа и полным списком работ.
6. Фраза `Покажи ТРЗ за 28.07.2026` строит отчёт, а не создаёт запись.
7. Повтор одного сообщения ТРЗ не создаёт дубль.
8. Вопрос, не требующий сведений о сотрудниках, не получает в промпте справочник
   всех участников.
9. Приложение импортируется и запускается с зависимостями из `requirements.txt`.

## Формат результата

Сначала перечисли найденные дефекты по критичности с файлами и строками. Затем
дай короткий план. После согласования или если явно разрешено сразу исправлять —
внеси минимальные изменения, добавь тесты, запусти их и покажи итоговый `git diff`.
Сообщи отдельно:

- что исправлено;
- что проверено автоматически;
- что нужно проверить вручную в Telegram;
- какие переменные Railway обязательны, какие опциональны;
- какие риски или этапы остались;
- хеш коммита, если изменения были закоммичены.

Не утверждай, что проблема решена, если тесты не запускались или деплой Railway
ещё не проверен. GitHub push выполняй только по прямому разрешению владельца.
